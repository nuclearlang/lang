# The `dart` dialect

How Nuclear is written in Dart, and in the frameworks built on Dart. The same Nuclear code is written once and the
transpiler turns it into each language and framework: this dialect only decides HOW the output is written in Dart
(templates, imports, the standard library), never what the Nuclear code is. Its framework dialect `flutter`
implements the [mobile platform](../../../nuclear-synapsis-framework/platforms/mobile/AGENTS.md) of Synapsis; what
that platform is (kinds, decorators, layout) is the platform's, not described here.

Paths in these documents are relative to this folder (`nuclearlang/dialects/dart/`). `../../` is the language
project ([its AGENTS.md](../../AGENTS.md)); `../../../` is the root of the tree.

## Stack

- Target: Dart 3; the output passes `flutter analyze` with `flutter_lints`, 0 warnings.
- The dialect: TOML tables and Mustache-subset templates, read at run time by `../../crates/nuclear-dialect`.
- `flutter` (platform `mobile`): Flutter, with `bloc` / `flutter_bloc`, `json_serializable` / `json_annotation`,
  `get_it`, `dio`, `go_router`, `fpdart`, `connectivity_plus`, `flutter_secure_storage`; tests with `flutter_test`,
  `mocktail` and `bloc_test`. Runtime: the platform's Dart package `synapsis` (and `synapsis_genkit` for the
  `genkit` plugin).
- Type definitions: `dart@3.13.5`, `flutter@3.47.7` and the packages of the `flutter` dialect, generated by
  `../../tools/defs/` (Dart, `package:analyzer`) from the installed Flutter SDK.

## Commands

```sh
# from the root of the tree
cargo test                                     # goldens (base.dart, the flutter examples and projects), validation, editor docs
UPDATE_GOLDEN=1 cargo test -p nuclear-transpile    # accept a changed output, then review the diff
cargo run -q -p nuclear-cli -- build <file.nuc> --dialect flutter [-o out.dart]
cargo run -q -p nuclear-cli -- dialect check dart        # or flutter
cargo run -q -p nuclear-cli -- spec --dialect flutter    # the contract: templates, variables, options
nuclear-synapsis-framework/platforms/mobile/checks/analyze-flutter.sh [file.nuc...]   # the examples under flutter analyze
nuclear-synapsis-framework/platforms/mobile/checks/spec-check-synapsis.py [--fix]    # the project blocks of flutter.md

# from nuclearlang/
tools/spec-check/check.py dialects/dart/docs/07-reference/dart.md dart dart [--fix]
tools/spec-check/check.py dialects/dart/docs/07-reference/flutter.md flutter dart [--fix]
tools/stdlib-check.sh [area...]                # the standard library in TypeScript, Dart and Python: the same output
FLUTTER_ROOT=<Flutter SDK> tools/defs/generate.sh    # regenerate defs/ (about 45 s)
```

What each check needs and proves: [docs/05-standards/testing.md](docs/05-standards/testing.md).

## Folders

- `dialect.toml`: `[options]`, `[syntax]`, `[types]`, `[operators]`, the kinds `extension`, `mixin` and `data`,
  modifiers, clauses, `[project]`, `[docs]`.
- `keywords.toml`: Dart's reserved words and how each is produced from Nuclear.
- `library.toml`: Nuclear's standard library written in Dart (one template per member).
- `docs.toml`: what the editor shows for each kind and header word.
- `templates/`: `extension.tpl`, `mixin.tpl`, `data.tpl`, `doc_comment.tpl`.
- `frameworks/flutter/`: the framework dialect (`dialect.toml`, `docs.toml`, `templates/`).
- `defs/<package>/<version>/`: type definitions. Generated.
- `docs/`: the context documentation (map below). `docs/07-reference/` and `docs/08-guides/` are normative and
  user texts, checked by tools and embedded in the `nuclear` binary.

## Rules of this project

- **The `.nuc` never bends to Dart.** Names are written as they are: Nuclear's `camelCase` is Dart's.
- **Nothing of Dart or Flutter in Rust.** Generic mechanisms belong in the compiler (projects, `decor`,
  `[decorators.args]`, `[architecture.names]`, call sites); a need of this target is asked as a generic `[options]`
  key or template variable (the language project decides it). Flutter specifics live here, as data.
- **The library is Nuclear's.** Every member of [the standard library](../../docs/07-reference/library.md) has its
  template in `library.toml`; a Dart name in Nuclear code, in a reference or in an example is a bug.
- **A framework dialect only writes the platform.** A kind, a decorator or a folder is added to the platform's
  contract first; `frameworks/flutter/` adds how it is written in Dart (ADR-dart-0001).
- The generated code is what an expert would write: `const` constructors, no layer that adds nothing at run time;
  it passes `flutter analyze` without warnings.
- The automatic imports of the SDK and of the packages come from the type definitions (`[dialect] defs`), not from
  hand-written lists. An `[auto_imports]` entry exists only for a package without definitions (`fpdart`, the test
  libraries) or to choose the module of a name two packages export.
- `docs/07-reference/dart.md` and `flutter.md` hold only final rules and real equivalences (`spec-check` and
  `spec-check-synapsis.py`, 0 problems). Never edit an equivalence by hand: change the dialect, then `--fix`.
- Every kind, decorator and header word has its entry in `docs.toml` (test `every_dialect_word_has_editor_docs`).
- `defs/` is generated: never edited. After a version or the runtime's API changes, regenerate it
  ([runbook](docs/06-runbooks/type-definitions.md)) and update the `defs` lists.
- Output changed: `UPDATE_GOLDEN=1 cargo test`, the diff reviewed, the reference fixed in the same change.
- A structural decision (a library, a pattern of the generated code) is a new ADR in `docs/03-adr/`.
- What is not documented and cannot be read from the dialect files is asked, not invented.
