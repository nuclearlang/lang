# ADR-0001: The Smart Graph is a library of typed, linked, versioned rows

## Context and problem
The knowledge base of the AI loop (ADR-platform-0003) was two collections made by cutting every markdown file of the
tree into pieces of 1400 characters. A piece knew its file and little else. Asking "what is nuclear" answered the
agent skill and a chapter about modules; "advantages" answered an editor's README; an error code found its table
cut in the middle. Nothing said what the ecosystem is for, what it can and cannot do, which tool does what, how a
task is done or what an error has to do with another. The log of the project's state was read by the local agents.
And nothing kept the base in step with the code: it was rebuilt when someone remembered.

The user asks for a library that knows the theory, the documentation, the rules, the purpose and every tool; what
Nuclear can and cannot do; every error and how errors relate; organised as JSON assets with their metadata in
Chroma collections designed for what Chroma can do; with versions, updated with every feature; tested with the
questions people ask; good enough to replace the markdown files one day.

Chroma gives collections with their own metadata, rows with a vector, a document and metadata of texts, numbers,
booleans and lists of texts, filters over that metadata (`$contains` on a list) and lookup by id. Its full-text
filters read the document, which this graph stores encrypted, so they are of no use here; it has no keyword index.

## Decision
**Shelves.** One Chroma collection per kind of question, each with its own row types and filters: `concepts`,
`language`, `platforms`, `tools`, `errors`, `capabilities`, `playbooks`, `examples`, `docs`. `shelves.nuc` is the
schema; the base carries it as `schema.json`. `prompts` (the prompt files of the package) and `memory` (what an
agent keeps about a project) are collections outside the base. The catalogue of exact questions, `queries`, is a
tenth shelf (ADR-graph-0002).

**A row is a card.** `id` (`<prefix>:<name>`; a prefix belongs to one shelf, so an id is fetched without a search),
`type`, `title`, `summary`, `body`, `keys` (exact names in lower case), `asks` (the questions it answers, as people
write them), `tags`, `platforms`, `agents`, `links` (`{rel, to}`), `sources`, `meta` (the shelf's own filters),
`data`. The metadata is stored in clear, as the vectors are; the document, encrypted, is the card. What is embedded
is not the document: the title in the embedding model's title slot, with the summary and the first 1200 characters
of the body; each `ask` is one more entry that points to its card.

**Search is by meaning and by exact name, over several shelves.** The query is embedded once and every shelf asked
answers its closest rows. The runs of one to four words of the query are looked up in the rows' `keys`: a row that
carries one is brought in and moves up, so a code, a command or a kind reaches its card whatever the rest of the
sentence says and whatever its language. Entries are ranked together, each card once; a `docs` row yields to a
card. A card is also read by id.

**The search is exact.** The vector Chroma keeps of every item a filter matches is compared with the query's;
Chroma's own index (HNSW) is not asked. It is approximate, and once rows were replaced it did not reach every item
it held, differently at every start. A shelf holds hundreds of items, so comparing them all costs milliseconds.

**Two readers, one flag.** `agents: false` marks what only frontier models and people read: the target languages,
the dialects underneath, the runtimes, the decisions, the state. A row the local agents read holds no code of a
target language.

**Assets.** The knowledge base is a folder of `assets/<shelf>/<name>.json`. A row with a structured source is
generated by `nuclear-graph knowledge build` and never written by hand; a row no file says in one place is curated
by hand and names its sources; an overlay merges hand-written fields into generated rows by id.

**The base is valid or it is not built.** `build` and `ingest` refuse a link to a row that does not exist, a
duplicated id, a prefix or a type of another shelf, a filter the shelf does not have, a missing title, summary or
body, target-language code in an agents' row, a diagnostic without documentation, a document no section claims.

**Versions.** `manifest.json` holds the schema, the revision (one more whenever any row changes, is added or is
removed), each row's hash and, for each curated row, the hash of each of its sources at its last review.
`revisions.json` is the log. The graph says which revision it holds.

**The base never stays behind the code.** `nuclear-graph knowledge check` fails when a generated file is not what
the tree gives now, a row is invalid, a source of a curated row changed since its review, or the running graph
holds another revision. The end-of-turn hook of the working tree runs it. The procedure is itself a row
(`playbook:update-the-knowledge-base`).

**What agents write at run time survives.** `POST /v1/documents` writes only `memory` and `examples`, as rows of
`origin: runtime` that an ingest keeps; the rows of the base are written by ingest alone.

**Retrieval is tested with people's questions.** `questions.toml` lists questions, in English and Spanish, and the
row each must return among the first; `nuclear-graph knowledge ask` runs them against the running graph. Every
```` ```nuclear ```` block of a hand-written row is compiled by `nuclear-graph knowledge examples`.

## Options considered
1. Document pieces: every markdown file cut into pieces, in one collection for everyone and one for the local
   agents. What was there; a piece answers no question whole.
2. A library of rows on shelves, generated where a structured source exists and curated where none does.
3. For the search, Chroma's approximate index against comparing every stored vector: the index lost cards after
   rows were replaced.

## Consequences
- Positive: the local agents stop reading document pieces. A coder gets the card of the kind it writes, validated
  examples of that kind and the pitfalls of that kind; a repair gets the card of each error code by id.
- Positive: a new command, MCP tool, kind, decorator, diagnostic, version or example reaches the base by building
  it; the check says when a hand-written row must be read again.
- Positive: the chat can answer what the ecosystem is for, what it can do and where the agent stops.
- Negative: a new capability, limit, failure or procedure needs its row written by hand.
- Negative: the help of the commands is read from the installed binaries: a changed command is installed before
  the base is built.
- Negative: keys are exact: a name written with a typo is found by meaning only.
- Negative: a curated row without `sources` is never asked for a review; one whose source is a long section is
  asked often.
- The pending work of the projects is not in the base: it changes with every task. What matters of it for a reader
  of the graph is in `capabilities` rows that name its sections as sources.
