# Changelog

All notable changes to nuclear are written here; versions follow [Semantic Versioning](https://semver.org).

## Unreleased

- The language server knows the helpers of the language (`chunk`, `uniqBy`, `Pair`...): completion offers them with their signature and doc comment, hover and signature help explain a call of one, like a function of the project (signature help now also answers for a function of another file of the project). A name the file, its project or the dialect has is never the helper. No go to definition: a helper has no file on an installed machine.
- **TypeORM is the rule of behaviour for migrations in every backend dialect** (ADR-backend-0002): the history is the table `migrations`, one row per migration applied (a database migrated by 0.91 or 0.92 is converted in place); the migrations are ordered by their timestamp, a pending one older than the applied ones runs, `nuclear migrate down` reverts the last one applied; new `--fake` (the history changes, nothing runs: a database that already has its tables comes under migrations) and `--transaction all|each|none` on `up` and `down`, **with `all` as the default** (it was one transaction per migration); `@created` / `@updated` are `NOT NULL DEFAULT CURRENT_TIMESTAMP`, a foreign key has only the rule its relation says, and SQLite's types have the same names, in `fastapi` and `nestjs` (the next `nuclear migrate make` of an existing project writes the change); `make` refuses a changed key. The MCP server's `project_migrate` takes `fake` and `transaction`. The database check fails on any difference between the schemas the dialects leave: there is none on SQLite, PostgreSQL, MySQL and MariaDB.
- The MCP server runs a project's tests: `project_test(project)` builds it and runs them with its dialect's runner, and answers the same in every dialect: how many passed and failed, each failure at its `.nuc` line, and what it means.
- The Smart Graph knows the helpers and the tests: a row per helper of the language (`lib:helper-<name>`: its signature, its meaning and the cases its tests state), the conformance, semantics and benchmark programs as examples with what they print, and what can be answered about them (`can:helpers`, `can:tested-in-every-dialect`, `can:backend-errors`), with the questions the chat is held to.
- The decisions that frame the language's stability and the dialects' parity are one record: ADR-platform-0014 (root rule 16).
- The MCP server makes and applies migrations: `project_migrate(project, action)` with `status`, `make` (`message`), `up` and `down` (`to`: up to, or back to, a migration), the same in every backend dialect. `make`, `up` and `down` ask the user first (a question, or a preview and its token): `up` and `down` change the database of the project's active environment. `nuclear_project` no longer runs `migrate`, which asked nothing.
- **One body for every error and one OpenAPI document, in every backend dialect** (ADR-synapsis-0013): an error answers `{ "status", "message" }`, and an invalid body or parameter adds `errors`, one reason per field (`field`, `rule`, `message`) in Nuclear's words; each runtime converts what its framework reports. `GET /openapi.json` answers the document the transpiler writes from the project, the same in `fastapi` and `nestjs`. A client that read `detail` or `statusCode` reads `message` and `status`.
- **Migrations that behave the same in every backend dialect and database**: `nuclear migrate status`, `nuclear migrate [up] --to <migration>`, `nuclear migrate down --to <migration>`; one transaction per migration (a failed one is never recorded); every unique and foreign key named the same; `make` also warns of a required column added without a default; a database that already has the tables, a migration applied and missing from the folder and two migrations made after the same one are refused with the same message. Fixes: in `nestjs` on SQLite, changing or dropping a column deleted the rows of the tables that pointed to it, a removed unique or foreign key stayed in the database, and a failing migration left half of itself; in `fastapi`, adding or dropping a unique failed, and SQLite's schema changes ran outside the transaction. `nuclear migrate` runs from a build of the tree. The database check runs 11 migration scenarios through the real command on SQLite, PostgreSQL, MySQL and MariaDB.
- **The helpers of lodash are part of the language** (ADR-lang-0013): `chunk`, `uniqBy`, `partition`, `orderBy`, `camelCase`, `pick`, `get`, `merge`, `memoize` and the rest (117, `nuclear help helpers`) are called with no `use`, in every dialect of every platform. The transpiler writes only the helpers a program calls, with the ones they call: into the file itself when it is built alone, into one generated file of the project (`nuclear_helpers`) that each file imports from by name. A program that calls none is exactly what it was. A local, a member, a declaration of the project or a name imported with `use` is always the program's own; a helper wins over a function a target has under the same name.
- **The helpers of lodash, in Nuclear** (`nuclear-synapsis-framework/lodash`): 121 functions over lists, maps, texts, numbers and functions (`chunk`, `difference`, `uniqBy`, `partition`, `orderBy`, `zip`, `camelCase`, `truncate`, `pick`, `get`, `set`, `merge`, `cloneDeep`, `memoize`, `once`, `flow`...), adapted to Nuclear (typed, a lambda as the iteratee, nothing the language's library already has), with 226 cases from lodash's own tests that print the same in TypeScript, Dart and Python. What writing it fixed in the compiler: a lambda takes its parameters' types from the function it is given to; `slice` and `substring` out of range are clamped the same in every target (Dart threw, TypeScript swapped the ends); a method given as a value keeps its object in TypeScript; `x is <string, any>` works in TypeScript and Python and `x is T[]` asks the same in Dart; two texts are compared with `<` in Dart; a map or list literal inside `any` data accepts any value in Dart; a value declared `any` and a nullable decimal are printed the same everywhere; `find()?.name` makes its call once in Python; type parameters named `A`, `B` and declarations named like a word of the target (`range`) are imported right between the files of a project; a parameter list split over lines compiles in Dart.
- **A backend checked against real databases** (`platforms/backend/checks/database-check`, Docker): the same Nuclear project (`store_api`: relations, pagination, a transaction that rolls back, validation, conflicts) built with `fastapi` and `nestjs` on SQLite, PostgreSQL, MySQL and MariaDB: migrations made, applied, read back from the schema, extended on a table with rows and reverted; 57 answers over HTTP that must be byte-identical in both dialects on every database; its unit tests. Fixes it found: in `fastapi` a `DateTime` lost its time zone and its JSON was not `toIso()`'s, changing a row with `@updated` answered 500, route parameters of several words did not bind, a related row carried Python's names, a `@manyToMany` list set on a found row failed, `MariaDB(url)` could not be imported, a `string` column had no length on MySQL; in `nestjs` `ilike` failed off PostgreSQL, a null column was missing from the answer of a create, a `@manyToMany` row carried its join row and a list of texts in a model was validated as one text. Fix (the compiler): `repository.where(...).count()` was written as a list's `count`.
- The generated code measured against an expert's in eight programs (`nuclear-synapsis-framework/eval/thesis/bench`: n-body, binary trees, fannkuch, a collections pipeline, texts, calls, primes, word frequencies), and what they showed fixed: Python reads a map as an expert does (`m.get(k, 0)`, `m[k]`, no helper call in a loop), `sortedBy` / `sortBy` read each key once in TypeScript and Dart and keep the order of equal keys in Dart (its sort did not promise it). Fix (texts are data): the replacement of `replace` / `replaceAll` is never a pattern (JavaScript read `$&` and `$1`, Python's regex `\\1`), `replace` with a `Regex` replaces the first match only in TypeScript and works in Python, and a doc comment with a `\\` is a valid Python docstring.
- **The language's conformance programs** (`nuclearlang/examples/conformance`): every operator, statement and feature of the language as one program per area, built for TypeScript, Dart and Python, checked with each target's own tools with no warning allowed, run and compared; the three must print the same text, on every change of the transpiler (the CI's `language` workflow). Fixes they found: `-(-x)` was a decrement in TypeScript and Dart; a compound assignment as the last line of a typed function returned nothing; a map pattern (`{ low, high } = m`) was not Python; a block lambda that changes a variable of its function failed in Python (`nonlocal`); an optional attribute never set did not exist in Python; `Stack<int>()` and `first<int>(xs)` passed the type as a value in Python; an integer given for a `double` printed without its decimals in Python; an inverted range threw in Dart; `"${true}"`, the sum of a `double[]` and `isOk` of a kept `Result` did not compile in Dart; a local named like a library function (`log`) imported `dart:math`; TypeScript printed the sum of unknown numbers as a decimal, a missing optional attribute as `undefined`, a getter's decimal and a joined list of decimals without `.0`, and compared `m[k] == null` by content; a helper was written for a form that never calls it. New: a function may return a function type (`adder(n: int) (x: int) => int`), a variable is narrowed inside `if x is T`, and type parameters reach the library (`Box("hi").get().upper()`).
- Fix (found on a clean machine in Docker): the welcome's app name, a team without members, the installer's editor box wording.
- The automatic update: every use of NuclearLang (the `nuclear` command, VS Code, the MCP server) looks for a newer release once a day; it installs itself when the user stops working (30 minutes without a use) or within 12 hours. `nuclear update --auto off`, the setting `nuclear.update.auto` or `NUCLEAR_AUTO_UPDATE=0` turn it off.
- Fix (the editor): the Nuclear workspace follows VS Code's folder as VS Code does: no project of another window, nor a deleted one, nor the last workspace opened elsewhere.
- Nuclear Chat renders an agent's Markdown tables, headings, rules, numbered, task and nested lists.
- Fix (the editor): a workspace deleted from the disk no longer blocks the extension: the welcome starts again from creating or opening one, and nothing makes the deleted folder again.
- The editor: a workspace or an app deleted from the disk is shown crossed out, never used (Nuclear Atlas failed on its folder); the welcome asks only what matters (the spending, the notices, the chat's colors); the teams, the reports and Nuclear Builder in a calmer look (*Sala de control*).
- **Nuclear Builder for big work, told as a story** (spec 024): an agent measures a task before the work (≤ 3 files and ≤ 100 lines small, ≤ 10 files and ≤ 400 lines medium: its own; larger, a new feature or several specs: it proposes Nuclear Builder with its count as the reason; playbook `size-a-task`). A run takes several specs (`run_start` `specs`), worked in order, one bill. The specs' language is asked once per project (the editor's offered; `spec new --language`, `spec_create` `language`, kept as `specLanguage`), their headings included.
- A failure is diagnosed and repaired (spec 024): one diagnosis call reads the failure; when it can be fixed the station works once more with it (a failed Quality sends its findings to the Code station); what a station cannot fix alone is asked of the user with its diagnosis (the run waits on `decide-<station>`: a change with the user's decision works it once more, an approval goes on). A check fixes what it finds and fails only for what it could not; what only the user can decide (the CI host, a repository) is listed at the station's gate, once. The repairs count in the run's budget and are said in the team's channel.
- `ci_preview` (and `nuclear-builder export --print`): the CI file the line would write and whether the project's is the same, without writing it. The developer's "tests first" check passes when the new tests fail before their code (`expect = "fail"`); a gate's own user checks (`gate = true`) are answered by its yes. The design cites only the project's ADRs.
- A backend lets the web apps of its config's origins call it (CORS): `origins: string[]` in the `appConfig`, the same in nestjs and fastapi. An invalid body is a 400 in every backend dialect (the fastapi documentation said 422).
- **A channel is a memory** (spec 023 requirement 8): a team's channel is its tech lead, exactly as its direct message (the same prompt, tools, spending and run reports; another team's channel, that team's lead). Every channel, thread and direct message keeps its own durable memory, `.nuclear/builder/chat/memory/<channel>[/<thread>].jsonl`, written without a model call (the user's requests, the specs written, the runs started with their state, the plans stated, the open questions, a line per message older than the chat's 40-message window), given to the member as *What this channel remembers* (newest first, capped) and read only in that channel. `nuclear-builder chat memory <channel> [--thread <t>] [--clear] --json` shows or forgets it. The tech lead's plan starts with a line `Plan: …`.
- **Teams that work like human teams** (spec 023, the engine): Nuclear Atlas only informs (Nuclear, the workspace and the projects, from the Smart Graph); asked for a task it names the free teams (no run in progress) with their tech lead, or offers to make one with the MCP server's team tools; its MCP servers run with `--informs` (`nuclear-mcp --informs`, `nuclear-builder mcp --informs`: no tool that writes a spec, starts a run or builds). The tech lead's first answer to a task is the plan: what, through which stations, who of the team does each part; then the spec and the run. A team has its `method` (Scrum by default) and `instructions`, in every member's prompt (`nuclear-builder team update --method … --instructions …`), and a model for every member (`--kind --provider --model`, `--no-brain`; a member's own wins, `team member update --team-brain` gives it back; `team show` gives each member's `inheritsBrain`). `team list` gives each team's `lead`, its runs in progress and whether it is `free`. `chat-host` gives every team, only the tech leads and Atlas `listed`; Nuclear Chat opens a direct message only for a listed member, keeps the older ones readable (out of the sidebar, found by the switcher). The spending is asked only for an API paid by use; an agent's subscription is not asked unless `forceConfirm`. The MCP server's `team_create` and `team_edit` take `method`, `instructions`, `kind`, `provider`, `model`. Teams of before read as Scrum, without a brain, every member its own.
- The release publishes the extension's checksum (`nuclearlang-<version>.vsix.sha256`): the extension checks against it a file it must take from the release when its own copy is missing.
- Fix (VS Code): the onboarding is resumed where it was after *This window* reloads the editor, a new window or a closed editor (its progress kept by the editor and saved before the reload), the AI services' set-up is its last step until it is finished or declined, and a 0.84.0 welcome never finished comes back once; Nuclear Atlas's chat works before there is an app (on the workspace's folder).
- The editor's Nuclear workspaces (spec 022, VS Code): the workspace holding VS Code's folder (else the last one opened) with its apps as the strip's tabs, the recent workspaces and the projects opened by hand kept by the editor (never lost when VS Code changes folder), *Create / Open a Workspace*, *Add / Remove / Rename an App*, an empty panel that says why, and a welcome in three steps (the workspace, its apps, a tour of each tool) with *Do it with me by chat* through Nuclear Atlas and the MCP server. Nuclear Builder shows a spec written by the MCP server at once. The tutorial and the Synapsis guide start from a workspace, by chat.
- The MCP server organizes the user's work (spec 022): `workspace_create`, `workspace_show`, `workspace_edit`, `workspace_delete`, `app_add`, `app_rename`, `app_remove` (`nuclear workspace`); `spec_create`, `spec_list`, `spec_show`, `spec_edit` (written where Nuclear Builder reads them); `team_list`, `team_show`, `team_create`, `team_edit`, `team_delete`, `member_add`, `member_edit`, `member_remove`, `skills_set` (never a local member). Nuclear Builder has `spec update <id> --stdin` and its tool `spec_update` (the user's). What an agent cannot do yet through the server: `docs/04-specs/022-workspaces-and-mcp/mcp-coverage.md`.
- A service that does not answer at the end of the set-up (found on a new Mac: Nuclear Chat) is waited for, started again and, when another program holds its port without answering, moved to a free port; the port of our own service that is still starting is no longer moved under it; another copy of a service (an older version's, a source install's, one started by hand) is stopped, so one runs; a failure shows the service's own last lines. `installer/tests/stack.sh` checks the stack a real machine is left with.

- An update downloads the vectors of the knowledge base only when they changed: the release's SHA-256 is asked first, and vectors already here with that checksum are kept (`fetchVectors`, Nuclear Builder's set-up).
- The local models are on standby (ADR-platform-0013): `"localModels": false` in Nuclear Builder's `setup.json`.
  `nuclear-builder setup` offers only the profile `remote`, which now runs the Smart Graph and Nuclear Chat;
  `--profile lite|medium|hard` is refused as on standby; on a machine that had a local profile its first step takes
  away what NuclearLang put there (the Developer's service and launcher, the models it pulled, Ollama when it

  `localModels`; `agents`, `models` and `team screen` list no local kind nor Ollama model. A member or tech lead of

  Gemini CLI, Cursor, OpenCode, Grok Build; else an API provider with a key), told in the team's `warnings`, the file

  local Developer. Nuclear Chat's agent picker falls back to the first agent there, never a local one.
- Environments (spec 021, ADR-platform-0012): every `env("NAME")` / `env("NAME", "default")` of a platform project
  is listed in `.nuclear/contract.json` (`env`: name, default, required, client, uses); a name or default that is not
  a text literal is N0310; N0311 (a secret read by a client) and N0312 (a required variable without a value) are
  documented. `Manifest::env` gives a client build its values: the react dialect writes `src/nuclear_env.ts`, the
  flutter dialect `lib/nuclear_env.dart` (only the variables the code reads), and `env()` is their function. The
  templates' new filter `escape:"$"`; a file built alone knows the names of its dialect's project files.
- The values of `config.nuc` (`app(description, version)`, a package's name, version and path) are escaped for the
  file they go into: the templates' new filters `json` / `toml` and `html`, and the pubspec's YAML; a description
  can no longer add keys (an npm `postinstall`, a TOML dependency) or a `<script>` to the built site (spec 018 M6).
- Nesting deeper than 200 levels (expressions, blocks, types) is the error N0023, instead of a stack overflow that
  aborted `nuclear check` and the language server on one file (spec 018 M8).
- Any package of the target is used through Nuclear (ADR-lang-0008). A name called like its package is imported by name
  (`from tqdm import tqdm`, `import { nanoid } from 'nanoid'`; before, as the package itself); `index.json` has
  `defaults`, a package's default export (`import dayjs from 'dayjs'`), which `gen.js` now describes; `config.nuc`
  takes a name that is not an identifier (`"date-fns@^4.1.0"`); `[project.manifest.advice]`; `nuclear defs` reads the
  packages of the project it runs in; `gen.py --distribution` and `gen.js --package`; `defs.dart` skips the library of
  a plugin the app has not enabled (it failed every `flutter add` there). A member of a module (`np.max(list)` after
  `use numpy as np`) or of a library's function or object (`lodash.map(...)`) is the library's own: it was rewritten
  as the member of Nuclear's library with that name (`_max(np)`).
