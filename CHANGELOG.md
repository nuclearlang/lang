# Changelog

All notable changes to nuclear are written here; versions follow [Semantic Versioning](https://semver.org).

## Unreleased

- Nuclear Chat renders an agent's Markdown tables, headings, rules, numbered, task and nested lists.
- Fix (the editor): a workspace deleted from the disk no longer blocks the extension: the welcome starts again from creating or opening one, and nothing makes the deleted folder again.
- The editor: a workspace or an app deleted from the disk is shown crossed out, never used (Nuclear Atlas failed on its folder); the welcome asks only what matters (the spending, the notices, the chat's colors); the teams, the reports and Nuclear Builder in a calmer look (*Sala de control*).
- **Nuclear Builder for big work, told as a story** (spec 024): an agent measures a task before the work (≤ 3 files and ≤ 100 lines small, ≤ 10 files and ≤ 400 lines medium: its own; larger, a new feature or several specs: it proposes Nuclear Builder with its count as the reason; playbook `size-a-task`). A run takes several specs (`run_start` `specs`), worked in order, one bill. The specs' language is asked once per project (the editor's offered; `spec new --language`, `spec_create` `language`, kept as `specLanguage`), their headings included.
- A failure is diagnosed and repaired (spec 024): one diagnosis call reads the failure; when it can be fixed the station works once more with it (a failed Quality sends its findings to the Code station); what a station cannot fix alone is asked of the user with its diagnosis (the run waits on `decide-<station>`: a change with the user's decision works it once more, an approval goes on). A check fixes what it finds and fails only for what it could not; what only the user can decide (the CI host, a repository) is listed at the station's gate, once. The repairs count in the run's budget and are said in the team's channel.
- `ci_preview` (and `nuclear-builder export --print`): the CI file the line would write and whether the project's is the same, without writing it. The developer's "tests first" check passes when the new tests fail before their code (`expect = "fail"`); a gate's own user checks (`gate = true`) are answered by its yes. The design cites only the project's ADRs.
- A backend lets the web apps of its config's origins call it (CORS): `origins: string[]` in the `appConfig`, the same in nestjs and fastapi. An invalid body is a 400 in every backend dialect (the fastapi documentation said 422).
- **A channel is a memory** (spec 023 requirement 8): a team's channel is its tech lead, exactly as its direct message (the same prompt, tools, spending and run reports; another team's channel, that team's lead). Every channel, thread and direct message keeps its own durable memory, `.nuclear/builder/chat/memory/<channel>[/<thread>].jsonl`, written without a model call (the user's requests, the specs written, the runs started with their state, the plans stated, the open questions, a line per message older than the chat's 40-message window), given to the member as *What this channel remembers* (newest first, capped) and read only in that channel. `nuclear-builder chat memory <channel> [--thread <t>] [--clear] --json` shows or forgets it. The tech lead's plan starts with a line `Plan: …`.
- **Teams that work like human teams** (spec 023, the engine): Nuclear Atlas only informs (Nuclear, the workspace and the projects, from the Smart Graph); asked for a task it names the free teams (no run in progress) with their tech lead, or offers to make one with the MCP server's team tools; its MCP servers run with `--informs` (`nuclear-mcp --informs`, `nuclear-builder mcp --informs`: no tool that writes a spec, starts a run or builds). The tech lead's first answer to a task is the plan: what, through which stations, who of the team does each part; then the spec and the run. A team has its `method` (Scrum by default) and `instructions`, in every member's prompt (`nuclear-builder team update --method … --instructions …`), and a model for every member (`--kind --provider --model`, `--no-brain`; a member's own wins, `team member update --team-brain` gives it back; `team show` gives each member's `inheritsBrain`). `team list` gives each team's `lead`, its runs in progress and whether it is `free`. `chat-host` gives every team, only the tech leads and Atlas `listed`; Nuclear Chat opens a direct message only for a listed member, keeps the older ones readable (out of the sidebar, found by the switcher). The spending is asked only for an API paid by use; an agent's subscription is not asked unless `forceConfirm`. The MCP server's `team_create` and `team_edit` take `method`, `instructions`, `kind`, `provider`, `model`. Teams of before read as Scrum, without a brain, every member its own.
- The release publishes the extension's checksum (`nuclearlang-<version>.vsix.sha256`): the extension checks against it a file it must take from the release when its own copy is missing.
- Fix (VS Code): the onboarding is resumed where it was after *This window* reloads the editor, a new window or a closed editor (its progress kept by the editor and saved before the reload), the AI services' set-up is its last step until it is finished or declined, and a 0.84.0 welcome never finished comes back once; Nuclear Atlas's chat works before there is an app (on the workspace's folder).
- The editor's Nuclear workspaces (spec 022, VS Code): the workspace holding VS Code's folder (else the last one opened) with its apps as the strip's tabs, the recent workspaces and the projects opened by hand kept by the editor (never lost when VS Code changes folder), *Create / Open a Workspace*, *Add / Remove / Rename an App*, an empty panel that says why, and a welcome in three steps (the workspace, its apps, a tour of each tool) with *Do it with me by chat* through Nuclear Atlas and the MCP server. Nuclear Builder shows a spec written by the MCP server at once. The tutorial and the Synapsis guide start from a workspace, by chat.
- The MCP server organizes the user's work (spec 022): `workspace_create`, `workspace_show`, `workspace_edit`, `workspace_delete`, `app_add`, `app_rename`, `app_remove` (`nuclear workspace`); `spec_create`, `spec_list`, `spec_show`, `spec_edit` (written where Nuclear Builder reads them); `team_list`, `team_show`, `team_create`, `team_edit`, `team_delete`, `member_add`, `member_edit`, `member_remove`, `skills_set` (never a local member). Every change asks the user first: MCP elicitation, or for a client without it a preview and a `confirm` token valid once for 5 minutes for that exact change. A folder is deleted only when the call says so. Its instructions and `nuclear_start` start the work from a workspace. Nuclear Builder has `spec update <id> --stdin` and its tool `spec_update` (the user's). What an agent cannot do yet through the server: `docs/04-specs/022-workspaces-and-mcp/mcp-coverage.md`.
- A service that does not answer at the end of the set-up (found on a new Mac: Nuclear Chat) is waited for, started again and, when another program holds its port without answering, moved to a free port; the port of our own service that is still starting is no longer moved under it; another copy of a service (an older version's, a source install's, one started by hand) is stopped, so one runs; a failure shows the service's own last lines. `installer/tests/stack.sh` checks the stack a real machine is left with.
- The delivery gate: `installer/release/delivery.sh <version>` must pass before a tag (version check, `cargo test`, clippy with 0 warnings, the VS Code extension's compile and tests, Nuclear Builder's, the MCP server's and the backend runtimes' tests, the website exactly as its workflow, `knowledge check`, the archive and every installer test), and `installer/release/after-release.sh <version>` after it (every workflow green, every asset, the site serving the tag's installers, the public one-liner and an update from the previous release in a fake HOME).
- The installer's tests read what the user reads: `OUT1` runs the installer in a terminal of 80 and 60 columns with colors and checks the rendered screen (no internal text, the motto once, no `nuclear intro`, every box's border in its column, no box line wrapped); `UPD1` updates the previous published release and runs `nuclear update` through the installer's link. `NUCLEAR_UPDATE_DRYRUN=1 nuclear update` prints what it would run.
- Fix: in a terminal narrower than a box's text the installer wrapped it past the border (the summary at 60 columns, the header's pixel letters); such a line is now wrapped inside the box, and a narrow terminal gets the header in words. The turning sign's lines are cut to the terminal, so a long one no longer leaves its frames on the screen.

- The installer says only what the user needs: the sign and the motto once (no second banner, no intro), no ADR or internal note, no profile boxes when there is nothing to choose, and boxes that never cut their text.
- `nuclear update` with the latest release already here says so and runs nothing; `--reinstall` installs it all the same.
- The website is published again (its check failed since 0.82.0: the web onboarding example was not what `nuclear new` writes now, `env("API_URL", …)`), so `nuclearlang.github.io/install.sh` is the release's installer again instead of an older one.
- An update downloads the vectors of the knowledge base only when they changed: the release's SHA-256 is asked first, and vectors already here with that checksum are kept (`fetchVectors`, Nuclear Builder's set-up).
- The local models are on standby (ADR-platform-0013): `"localModels": false` in Nuclear Builder's `setup.json`.
  `nuclear-builder setup` offers only the profile `remote`, which now runs the Smart Graph and Nuclear Chat;
  `--profile lite|medium|hard` is refused as on standby; on a machine that had a local profile its first step takes
  away what NuclearLang put there (the Developer's service and launcher, the models it pulled, Ollama when it
  installed it), writes `ai.env` as `remote` and says the GB freed. `setup --plan --json` and `team screen` carry
  `localModels`; `agents`, `models` and `team screen` list no local kind nor Ollama model. A member or tech lead of
  the local kind is worked, on read, by the default external choice (the first agent installed: Claude Code, Codex,
  Gemini CLI, Cursor, OpenCode, Grok Build; else an API provider with a key), told in the team's `warnings`, the file
  of before kept as `.bak`; the chat's general agent defaults to that choice too. The installers never install
  Ollama, a local model or the Developer (a remembered local profile becomes `remote`). The MCP server registers no
  `developer_*` tool (`LOCAL_MODELS`, held to `setup.json` by a test) and `nuclear_start` never sends an agent to the
  local Developer. Nuclear Chat's agent picker falls back to the first agent there, never a local one.
- Environments (spec 021, ADR-platform-0012): every `env("NAME")` / `env("NAME", "default")` of a platform project
  is listed in `.nuclear/contract.json` (`env`: name, default, required, client, uses); a name or default that is not
  a text literal is N0310; N0311 (a secret read by a client) and N0312 (a required variable without a value) are
  documented. `Manifest::env` gives a client build its values: the react dialect writes `src/nuclear_env.ts`, the
  flutter dialect `lib/nuclear_env.dart` (only the variables the code reads), and `env()` is their function. The
  templates' new filter `escape:"$"`; a file built alone knows the names of its dialect's project files.
- The values of `config.nuc` (`app(description, version)`, a package's name, version and path) are escaped for the
  file they go into: the templates' new filters `json` / `toml` and `html`, and the pubspec's YAML; a description
  can no longer add keys (an npm `postinstall`, a TOML dependency) or a `<script>` to the built site (spec 018 M6).
- Nesting deeper than 200 levels (expressions, blocks, types) is the error N0023, instead of a stack overflow that
  aborted `nuclear check` and the language server on one file (spec 018 M8).
- Any package of the target is used through Nuclear (ADR-lang-0008). A name called like its package is imported by name
  (`from tqdm import tqdm`, `import { nanoid } from 'nanoid'`; before, as the package itself); `index.json` has
  `defaults`, a package's default export (`import dayjs from 'dayjs'`), which `gen.js` now describes; `config.nuc`
  takes a name that is not an identifier (`"date-fns@^4.1.0"`); `[project.manifest.advice]`; `nuclear defs` reads the
  packages of the project it runs in; `gen.py --distribution` and `gen.js --package`; `defs.dart` skips the library of
  a plugin the app has not enabled (it failed every `flutter add` there). A member of a module (`np.max(list)` after
  `use numpy as np`) or of a library's function or object (`lodash.map(...)`) is the library's own: it was rewritten
  as the member of Nuclear's library with that name (`_max(np)`).
- First public version.
- `STATUS.md` holds only what is left to do (half done, untested, pending) and keeps no log: what a task did is written in the documentation of its area, and no file is made to hold history (`AGENTS.md` rule 6, `docs/context/workflow.md`); the start hook (`tools/context/check.sh session`) warns when the file is over 40 KB.
- `nuclear agent hook` checks a project with its own type definitions (`<project>/defs`), as `nuclear check` does: it reported every name of them as an error after each edit.
- The `try` template gets `catch_used` (the block names the caught value): the `python` dialect writes `except Exception:` when it does not, since a name nothing reads is an error of pyright's strict mode (`spec/python.md` §3.12).
- ADR-graph-0002: the planner of the Smart Graph runs an exact query only when its question is closer than the closest card; ADR-graph-0001: the graph's search is exact; ADR-installer-0002: a service that starts at login waits for the keyring.
- ADR-graph-0001: the Smart Graph is a library of typed, linked, versioned rows; the definition of done includes the knowledge base (`nuclear-graph knowledge build | check`, `ingest`) and the end-of-turn hook (`tools/context/check.sh stop`) runs the check.
- `[[generators]]` and `[gen]` in a platform's contract (`Dialect.generators`, `gen_values`); a facade alias named like its use case's field gets the field `<name>Instance` (ADR-codegen-0001).
- `nuclear_transpile::map::shape`: a declaration of a project as its source writes it (its file, its header's parameters, each method's parameters, return type and whether it awaits), which `nuclear gen usecase` reads; the `usecase` generator and whole-member merges in `spec/dialects.md` (ADR-codegen-0001).
- `docs/ai/mcp.md`: the MCP server's page (how to add it to each client, the order a model works in, every tool by group, what to do when one fails); the Builder page links to it.
- ADR-developer-0001: a strategy for each kind of request (a whole system, one screen, a rename, a failing test...), as rows of the Smart Graph that the analyst and the Builder follow; `docs/ai/loop.md` (the strategy of a request) and `docs/ai/mcp.md` (`graph_strategy`); the skill names it.
- ADR-installer-0002: the AI services come with the installer. Every release archive carries the code of the Smart Graph and the Nuclear Developer with its knowledge base (`ai/`, `tools/release/stage.sh`); the installers end with their set-up (`nuclear-builder setup`: a profile for the machine, the services at every login), bring a machine already set up to date without questions, and take `--no-ai` and `--profile <id>` (`-NoAi`, `-AiProfile` on Windows); `--uninstall` removes the services; `./install.sh --ai` is the same set-up over the working tree. `docs/ai/setup.md`; the release workflow clones the three AI repositories.
- `[project] package` in `nuclear.toml`: the package a project's files are emitted into (`build/<package>/...`; imports between the project's files are relative to it, `{{package}}` in a dialect's `project_import`); the `python` dialect uses it, so a Nuclear project is a Python package another tool can package (`spec/projects.md`, `spec/python.md`).
- ADR-graph-0002: questions with one right answer are answered from exact facts (SQLite, in the memory of the graph) by a query planner that asks no model; the Smart Graph is written in Nuclear (the `python` dialect), `tools/release/stage.sh` carries its `.nuc` sources and the set-up builds them; rule 12 of `AGENTS.md`: Nuclear and Synapsis first for every new development.
- ADR-platform-0003: any step, stage or run of the Builder runs again (`nuclear-builder retry <run> --step <id>`, `nuclear-builder restart <run>`), each step keeps the decisions it took and why, the run is drawn as a graph, and the acceptance criteria are held against what the run left (`docs/ai/loop.md`).
