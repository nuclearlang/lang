# Specs of the platform

A change that touches several projects. A change to one project is a spec in that project's `docs/04-specs/`.
One folder per change: `requirements.md`, `design.md`, `tasks.md`; `draft → approved → in-progress → done`.

| Spec | Change | State |
|---|---|---|
| [006-public-repositories](006-public-repositories/plan.md) | The organization and the split into public repositories | superseded by `ADR-platform-0002`; kept for what it says of the organization, the license and the published packages |
| [008-restructure](008-restructure/tasks.md) | One repository, a project per folder, per-project documents, the new names | done (2026-11-17) |
| [009-self-contained-ai-services](009-self-contained-ai-services/tasks.md) | The AI services ready to run from the installer: their own Python, Nuclear Builder in Nuclear, Ollama and the models by the user, the ports chosen | in progress (phases 1 and 2 done, phase 3 half done) |
| [010-migration-into-nuclear](010-migration-into-nuclear/requirements.md) | A TypeScript, Python or Dart project migrated into Nuclear: one meaning in every dialect, the points a tool cannot decide listed for an agent | draft |
| [011-software-factory](011-software-factory/requirements.md) | Nuclear Builder as a software factory: five roles as files (analyst, architect, developer, QA, DevOps), each done by the local agents, a provider's agent or a provider's model; a vault for keys; the plans as a console; the engine in Nuclear; the workbench (req. 19-26) | in progress |
| [012-observability](012-observability/requirements.md) | Traces, metrics and logs to Datadog, New Relic, Grafana or any OpenTelemetry collector: one connection in `config/`, the same Nuclear for every dialect | in progress (phase 1 done in `fastapi`; `nestjs` next) |
| [013-nuclear-chat](013-nuclear-chat/requirements.md) | Nuclear Chat, the factory's workplace as Slack: channels per team, direct messages with each member, threads per run and spec, members that ask and answer with their personality, GIFs; a component used by the Builder and Atlas | approved |
| [014-synapsis-real-time-and-embedded](014-synapsis-real-time-and-embedded/requirements.md) | Synapsis grows for Nuclear Chat: server-sent events in `backend`, a listening client and an embedded build in `web`, in every dialect | approved |
| [015-monitor](015-monitor/requirements.md) | Nuclear Monitor: each Nuclear function and method with its time, calls, connections and memory as a tree, written by the transpiler with `--monitor`, shown by the editor and read by the agents | in progress |
| [016-agent-onboarding](016-agent-onboarding/requirements.md) | An agent with no context learns Nuclear from the MCP server alone: `nuclear_start`, the atlas of topics embedded in the binary, the context documents `nuclear new` writes, every client integrated by the set-up, measured by a sandboxed run | in progress (phases 1-5 done; the other clients and the extension left) |
| [017-productivity-reports](017-productivity-reports/requirements.md) | Productivity and consumption: tokens, money, time, lines of code and results by agent, model, member, team and project, with charts; a command and an MCP tool | done (left: JetBrains window, CSV export, budgets and alerts: the Builder's roadmap) |
| [018-failure-matrix](018-failure-matrix/requirements.md) | Every machine, every state, fail-safe: the cases where NuclearLang can fail (systems, architectures, toolchains, editors, versions and upgrades, the user's choices, ports, our services, the LSP, permissions), each with its expected behaviour, its state and its test | draft (phase 1 half done: the update, the installers' choices and lock, sudo, the extension without NuclearLang) |
| [019-launch-and-growth](019-launch-and-growth/requirements.md) | **High priority.** Found by people, search engines and AI agents: the website readable without JavaScript, GEO, the MCP and package registries, the repository and organization ready, content, the launch as news, the community, open source, the names | in progress (phase 2 started) |
| [020-benchmark](020-benchmark/requirements.md) | **High priority.** Does Nuclear make cheap models build better software for less? Eight hard apps, Claude Code (Sonnet, Haiku), OpenCode (DeepSeek, flash), Cursor (Grok, Composer), with and without Nuclear, hidden tests, published | approved |
| [021-environments](021-environments/requirements.md) | **High priority.** Environments in every platform, like dotenv: `env("NAME", "default")` declares, `.env` files and the keyring hold the values, `--env <name>` picks one, web and mobile get them at build, `nuclear env` and the editor's Environments page edit them; ready for simulating an environment locally | in progress |
| [022-workspaces-and-mcp](022-workspaces-and-mcp/requirements.md) | **High priority.** A workspace (a folder with `.workspace/workspace.nuc`) organizes a business project and its apps; the editor remembers workspaces; the MCP server creates and edits workspaces, apps, specs, teams and members, always asking first; the onboarding by chat | in progress |
| [023-teams-like-human-teams](023-teams-like-human-teams/requirements.md) | **High priority.** Atlas informs and routes tasks to the tech leads; the chat lists only tech leads, who plan, explain and assign; each team has its method (Scrum by default) and instructions; spending asked only for API work; a team's model for all; every asset local, the release as contingency | in progress |
| [025-mcp-the-oracle](025-mcp-the-oracle/requirements.md) | **High priority.** The MCP server is the oracle: an agent asks it before opening a file; a small catalog per station, the project's map and compact results in one call, no reads of generated code, the prompt cache, a context preflight; a project's documents keep only its architecture and what is its own, and point to the oracle for the rest | approved |
